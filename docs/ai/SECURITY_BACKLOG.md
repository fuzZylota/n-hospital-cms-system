### F02 / A03 — user edit POST transaction boundary (2026-09-29)

`controllers/post/users/users.go:EditUser` uses `utilities.Orm.Pool.BeginTx` for this request only. `user_edit_transaction.go` locks actor and target `users` rows in UID order, reads the current active actor role and real target role/sid, applies the existing `user_edit_policy.go` allowlist, then checks active branch rows in sorted order. The user update and all `user_branch_permissions` updates/inserts share that transaction; affected rows, rollback and commit are checked. No raw DB error or account PII is returned or logged. A failed permission write rolls back an earlier user update. The existing HTTP 200 / JSON 201 success and nonadmin self-profile behavior remain. `user_edit_http_test.go` uses actual Fiber HTTP and a fake transactional driver for four roles, stale JWT role, self/other UID, protected fields, two branches, mid-request role change before the locked read, read/write/affected-row/rollback/commit failures, and atomic rollback of staged user/permission state. Offline targeted users tests, full users/post/lib module tests, and `go mod verify` in those three modules passed with the verified local module cache and network disabled. Source and synthetic-test confidence is high; real DB and production are **UNKNOWN**.

**Open product decisions:** Whether an admin may deactivate/demote self, whether the last active admin must be protected, and whether an admin may grant permissions outside their own branch are unchanged and require explicit policy approval. `schema.sql` has the `users` table but no `user_branch_permissions` DDL, so its real unique `(uid,sid)` constraint, existing duplicates, and conflict behavior are **UNKNOWN**. This package does not add a migration or promise that other writers cannot create duplicate permission rows. GET, add-user and ban-unban behavior is outside this fix. Real DB and production behavior are **UNKNOWN**.

### F06 / general file delete local evidence (2026-09-28)

- **Source / high confidence:** `baserouter.go` routes `POST /backend/add-file` and `/delete-file` through `PanelAuthMiddleware`; `GET /panel/dosyalar` uses the same `static/uploads` directory, while `dosyalar.js` sends only `file_name`. Neither general upload nor list creates/reads `medias`. The first delete fix incorrectly required a media row and broke ordinary deletion. The corrected endpoint requires the current admin principal, a flat name and `media_id=0`, checks the configured directory and regular file, then removes via Go `os.Root`. It never uses the client name as a path segment outside that confined root and does not change other media endpoints. Delete responses use fixed messages without server paths. The add response formerly returned a physical path in `data[0].url`; `homepage-content-duzenle.js` consumes that field for banner previews and stored values. The local change returns `/uploads/<URL-escaped saved flat name>` for single and numbered uploads, matching the list and static route; the panel strips the leading slash as before.
- **Local test / boundary:** Offline `go test ./custommediadelete -count=1` and `go test . -count=1` passed in `fiber-v2/controllers/post`. An in-memory Fiber test uses fake current-account and upload-policy readers, no ORM or DB, and actual `AddCustomMedia` → the same `lib.ReadDirectory` used by `ListFilesPage` → actual `DeleteCustomMedia` with synthetic Windows temporary files. It verifies the file appears then disappears, role downgrade/foreign ID/traversal denial, and an outside sentinel remains. Additional tests cover absolute/drive/backslash paths, missing/nonregular file, file and directory symlinks, fixed response messages, and fake upload-policy DB failure before a file is written.
